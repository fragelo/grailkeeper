01 POST /query:execute — Request Body

All parameters are passed as JSON in the POST body. The query field is the only logically required field. All others have sensible defaults.

JSON — Full Request Example 
{
  "query": "fetch logs, scanLimitGBytes:-1,
    bucket:{\"cdr-map\"}
    | filter imsi == \"222776780595499\"
    | fields timestamp, content, imsi
    | limit 50000",

  // Timeframe (override DQL from/to)
  "defaultTimeframeStart": "2026-04-07T20:13:57Z",
  "defaultTimeframeEnd":   "2026-04-08T20:13:57Z",

  // Result size limits
  "maxResultRecords": 50000,
  "maxResultBytes":   52428800,  // 50MB

  // Scan limits
  "defaultScanLimitGbytes": -1,      // unlimited

  // Timing
  "fetchTimeoutSeconds":         60,
  "requestTimeoutMilliseconds":  5000,

  // Sampling
  "defaultSamplingRatio": 1,       // 1 = no sampling

  // Optional
  "enablePreview": false,
  "includeTypes":  true,
  "locale": "en_US",
  "timezone": "UTC"
}
query
string($maxLength:1000000) REQUIRED
string
The full DQL query string. Max 1,000,000 chars. Timeframe in DQL takes precedence over defaultTimeframeStart/End. Always add bucket:{} for performance.
maxResultRecords
int64 · default: 1000 · min: 0 optional
integer
Max records returned. Default: 1000. No explicit upper bound but other limits apply. If exceeded, a warning is included in the response. Note: API is not designed for large-scale export — use windowed extraction.
maxResultBytes
int64 · min: 0 ⚠ avoid for extraction
integer
Max bytes for serialized result. Soft limit — final record that pushes over is still included. No default, no explicit upper bound. Warning: forces full dataset scan before truncating. Prefer maxResultRecords. API not designed for large-scale export.
defaultScanLimitGbytes
int32 · example: 100 · min: -1 optional
integer
Max GB to scan. Default configured at application level. Set -1 for unlimited. Can be overridden in DQL. Note: even with no limit, maxResultRecords, maxResultBytes, and timeouts still apply.
requestTimeoutMilliseconds
int64 · max: 60000 · min: 0 optional
integer
Max wait time before returning. If query finishes within this window → result returned (200). Otherwise → requestToken returned for polling (202). Max: 60,000ms. Excludes network transit time.
fetchTimeoutSeconds
int32 · example: 60 · min: 0 optional
integer
Soft time limit for fetching data. Further processing can happen after fetching. No explicit upper bound in API but application-level max applies. For large scans raise to 600s. Other limits (maxResultRecords) may still trigger.
defaultSamplingRatio
double · example: 1 · min: 1 optional
number
Default sampling ratio. By default no sampling is applied (1 = 100%). No upper limit but normalized to power of 10 ≤ 100,000. Use for dashboards/exploration only — never for extraction requiring completeness.
defaultTimeframeStart / End
string (ISO-8601 / RFC3339) optional
string
Query timeframe. Both must be set or both are ignored. Timeframe in DQL query string takes precedence. Example: 2026-04-07T20:13:57Z
enablePreview
boolean · default: false optional
boolean
If true, polling responses include intermediate preview results. Previews are always whole — never delta. If preview is available within requestTimeoutMilliseconds, returned in initial response.
includeTypes
boolean · default: true optional
boolean
Include field type information (types[]) in result. Default true. Set false to reduce response size when type info is not needed.
includeContributions
boolean · default: false optional
boolean
Include bucket contribution info in response metadata. When true, shows how each bucket contributed to the result — useful for debugging access and scan patterns.
enforceQueryConsumptionLimit
boolean optional
boolean
Enforce tenant-level query consumption limits. If true, query will fail if it would exceed the configured DDU consumption quota.
filterSegments
FilterSegments[] optional
array
Collection of filter segments for query-time data segmentation. Each segment has an id (string, required) and optional variables[] (name + values). Multiple segments combined with AND. Variables replace placeholders in segment definitions.
timezone
string · example: UTC optional
string
Query timezone. Defaults to UTC. Accepts IANA TZDB canonical names (Europe/Rome), abbreviated (CET), or UTC offset (+01:00).
locale
string · example: en_US optional
string
Query locale. ISO-639 language code + optional ISO-3166 country code. Examples: en, en_US, it_IT. If omitted, language/country neutral locale is used.
02 DQL Query Best Practices

✓ Always specify bucket

fetch logs, bucket:{"cdr-map"} — reduces scan from TB to GB. A bucket filter on the fetch command is processed before any table scan, dramatically reducing both scan time and DDU cost.

✓ Use filter for indexed fields

| filter imsi == "123..." — Grail stops early when an indexed field matches. Compare to | search imsi ~ "123..." which does a full text scan of all record content.

✓ Select only needed fields

| fields timestamp, content, imsi — reduces response size and transfer time significantly. Avoid returning all 40+ fields if you only need 3.

⚠ Avoid maxResultBytes for extraction

Setting maxResultBytes forces Grail to scan the entire dataset to measure bytes before truncating. For extraction use cases, rely only on maxResultRecords to allow early stopping.

⚠ | limit N in extraction DQL

Adding | limit 50000 in the DQL allows Grail to stop early once enough records are found — same mechanism the UI uses. This makes extraction as fast as interactive queries. Risk: if actual records exceed limit, data is incomplete.

✗ No scanLimitGbytes without -1

Default defaultScanLimitGbytes: 100 will truncate scans on large tenants (4.8TB/day). Always set -1 for production extraction to guarantee completeness.

⏱

TTL Critical — Poll within 60 seconds

The final result is guaranteed for only 1 minute after query completion. If you miss the polling window, the result is lost. Use a polling interval of 5–30 seconds.

types[ ] — Field Type Buckets

The types array maps field names to their types using index ranges. A single query can return records with different schemas if data was ingested with varying structures (called a "collision").

  • indexRange: [0, 99] → records 0 through 99 use this type mapping
  • indexRange: [100, 199] → records 100–199 may have different field types
  • Always look up type by finding the bucket where start ≤ record_index ≤ end

01 HTTP Status Codes & Client Action

The Grail API uses standard HTTP status codes. Each error includes a structured JSON body with error.details containing errorType, exceptionType, and the original queryString.

200

OK — Result Available Immediately

Query completed within requestTimeoutMilliseconds. The full result is in the body. progress will be 100 and state will be SUCCEEDED.

→ Parse result.records[] directly. No polling needed.
202

Accepted — Query Running Asynchronously

Query was accepted but not yet complete. Response contains requestToken and ttlSeconds. Poll /query:poll until state is SUCCEEDED.

→ Store requestToken. Begin polling every 5–30 seconds. Stop polling before ttlSeconds expires.
{ "requestToken": "D8DZEs1...", "state": "RUNNING", "ttlSeconds": 398 }
400

Bad Request — DQL Syntax Error or Invalid Parameters

The query string is malformed or an unsupported record type was specified. The details.syntaxErrorPosition field pinpoints the exact column and line of the error.

→ Do NOT retry. Fix the DQL query. Use /query:verify to validate before executing.

02 Result Truncation — Not an HTTP Error
⚠

RESULT_TRUNCATED — Returned with HTTP 200

When a query exceeds maxResultRecords or maxResultBytes, Grail returns HTTP 200 with a partial result and a RESULT_TRUNCATED error in the error details — NOT as an HTTP error code. Your client must explicitly check for this condition to detect incomplete data.

Truncation Detection (pseudo-code)
// After receiving HTTP 200:
if response.status == 200 AND response.state == "SUCCEEDED":
    records = response.result.records         # partial!
    is_truncated = (
        "RESULT_TRUNCATED" in response.stderr # dtctl flag
        or len(records) >= maxResultRecords     # count hit cap
        or response.error.details.errorType == "RESULT_TRUNCATED"
    )
    if is_truncated:
        # Split time window in half and re-query each half
        split_and_retry(window_start, window_end)

01 Client-Side Pagination Logic

The Grail Query API does not stream data — it returns a bounded result per call. A production client must implement windowed pagination: divide the time range into segments, query each segment, detect truncation, and split further if needed. This section shows the complete logic as a block diagram.

02 Truncation — The Core Pagination Mechanism

Unlike traditional REST APIs that use page tokens or offsets, Grail uses a truncation signal. When a window returns exactly maxResultRecords records, assume the result is incomplete and split the time window in half. This is the only reliable pagination mechanism.

AUTO-SPLIT — RECURSIVE HALVING
Window: Apr 7 00:00 → Apr 8 00:00 (cap: 500K)
Result: 500,000 records → TRUNCATED ✗
↓ split at midpoint
Apr 7 00:00 → Apr 7 12:00
Result: 500K → TRUNCATED ✗
Apr 7 12:00 → Apr 8 00:00
Result: 142K → OK ✓
↓ left side still truncated, split again
Apr 7 00:00 → Apr 7 06:00
Result: 380K → OK ✓
Apr 7 06:00 → Apr 7 12:00
Result: 310K → OK ✓
Total: 4 API calls · 832K records · 0 data loss
How to Detect Truncation
  • Primary: len(records) >= maxResultRecords
  • Secondary: RESULT_TRUNCATED in error details
  • Both checks needed — API may populate either or both
  • Truncation returns HTTP 200 — not a 4XX error
  • Only the records array is truncated — metadata is always complete
Why Time-Based Windows (not offsets)
  • Grail has no cursor/offset/page-token mechanism
  • Each window is an independent query with a time range
  • Windows are non-overlapping → no duplicates in output
  • Each window is independently resumable
  • Parallel execution of multiple windows is safe
03 Resume Pattern — Persistence Across Restarts

For large extractions spanning hours or days, the client must survive process restarts, network errors, and container reboots without losing progress or creating duplicates.

JOB STATE FILES — WHAT TO PERSIST
state.json

Current job status snapshot. Written atomically (temp file → rename) after every window. Used by UI/monitoring to show progress.

{
  "status": "running",
  "windows_done": 12,
  "total_windows": 48,
  "total_records": 487230,
  "progress_pct": 25.0
}
log.jsonl

Append-only event stream. Never overwritten. On resume, client reads this to determine which windows are already complete.

// one JSON per line:
{"type":"preflight_done", ...}
{"type":"window_done",
 "from":"2026-04-07T00",
 "to":"2026-04-07T06",
 "records":42150}
{"type":"window_done", ...}
output.jsonl

Append-only output file. Each window appends its records. On resume, new records are appended after existing ones — no rewrite, no duplicates.

// one JSON record per line:
{"timestamp":"2026-04-07T00:01:23Z",
 "content":"...",
 "imsi":"22277678..."}
{"timestamp":"2026-04-07T00:01:45Z",
 ...}
Resume logic: load log.jsonl → collect all window_done events → build set of (from, to) pairs → on next run, skip any window whose key is in that set
04 Parallel Execution

Multiple windows can be executed concurrently since each is an independent, non-overlapping time range. Parallelism reduces total wall-clock time for multi-window extractions but does not help single-window jobs.

When Parallelism Helps
  • Multi-window jobs: 7d+ ranges with many windows
  • Each window takes similar time → N workers → N× faster
  • Example: 48 windows × 20s each = 16 min sequential
  • With 3 workers: ~5.5 min (3× speedup)
Use ThreadPoolExecutor or asyncio — one worker per window
Parallelism Constraints
  • API query pool has limited concurrent slots
  • Too many parallel calls → HTTP 503 BUSY_SCHEDULER
  • Recommended: 1–3 parallel workers maximum
  • Output file must be protected by a write lock
  • Each worker needs its own temp buffer before appending
  • Single-window jobs: no benefit — use 1 worker
05 Key Implementation Rules

✓ Use maxResultRecords only — not maxResultBytes

Setting maxResultBytes forces a full dataset scan to measure bytes before truncating, eliminating all early-stop benefits. Use only maxResultRecords as the per-window cap.

✓ Set fetchTimeoutSeconds to 300 (5 minutes)

This keeps every API call within the guaranteed execution zone. Calls within this limit are guaranteed to either complete or timeout cleanly — no unexpected interruptions.

✓ Always add bucket:{} to DQL

fetch logs, bucket:{"your-bucket"} restricts the scan to a single bucket, dramatically reducing both scan time and query consumption. Without it, Grail scans all buckets.

⚠ Poll before TTL expires

Results are available for only 60 seconds after query completion. Poll at intervals of 5–30 seconds and stop polling at least 10 seconds before ttlSeconds expires. After the TTL, the result is permanently lost and the window must be re-queried.

⚠ filter vs search for indexed fields

| filter field == "value" uses indexes and stops scanning early. | search field ~ "value" performs a full text scan of all record content. Always prefer filter for known indexed fields.

✗ Never use subprocess PIPE for large responses

If wrapping a CLI tool via subprocess, never use stdout=PIPE. The OS pipe buffer (~64KB) will deadlock on responses larger than that. Write stdout directly to a temp file, then read the file after process completion.

04 Concurrency & Priority
Query Pool Priority

Grail manages multiple query pools with different priorities. API calls via /query:execute run in a shared pool alongside other workloads. During high-load periods, interactive and system workloads (alerting, automations) take precedence.

  • Alerting & anomaly detection — highest priority
  • Automation workflows
  • Interactive UI queries
  • REST API queries — shared pool
HTTP 503 — Scheduler Busy

When the query pool is at capacity, the API returns HTTP 503 with errorType: BUSY_SCHEDULER. This is a transient condition.

  • Implement exponential backoff: 10s → 20s → 40s → 80s
  • Maximum 5 retries before surfacing as an error
  • Reduce parallel workers to lower concurrent load
  • Schedule large extractions during off-peak hours
05 DQL Performance Guidelines

✓ Specify bucket in fetch command

fetch logs, bucket:{"your-bucket"} restricts the scan scope before any filtering. This is the single most impactful optimization — it can reduce scanned data by 6× or more compared to scanning all buckets.

✓ Use filter for indexed fields

| filter field == "value" uses column indexes and stops scanning early once all matching records are found. Significantly faster than | search which reads all record content.

✓ Select only required fields

| fields timestamp, content, imsi reduces the response payload. Returning all 40+ fields when only 3 are needed increases transfer time and response size unnecessarily.

⚠ Avoid maxResultBytes

This parameter forces Grail to measure the byte size of the full result before applying the limit. It eliminates early-stop optimizations. Use maxResultRecords exclusively for extraction use cases.

⚠ | limit N and completeness trade-off

Adding | limit N allows Grail to stop scanning once N records are found — same behavior as the interactive UI. This makes queries faster but risks missing records if actual count exceeds N. Only safe when N is significantly larger than expected record count.

⚠ scanLimitGbytes default may truncate

The default scan limit (typically 100GB at application level) will silently stop scanning on tenants with large data volumes. Always set scanLimitGbytes: -1 in extraction payloads to guarantee full coverage.

01 What is Grailkeeper?

Grailkeeper is a pure-Python bulk extraction tool built on top of the Grail Query API. It runs as a Docker container with a dark-themed web UI and solves the core problem of extracting millions of log records from Grail — something the /query:execute endpoint was not originally designed for.

Grail API design intent: The /query:execute endpoint is designed for interactive analytical queries, not bulk data export. It returns at most 500,000 records per call and responses can be 1–1.5 GB of JSON. Grailkeeper works around these limits systematically.

GitHub: github.com/fragelo/grailkeeper  ·  Current version: v4.0.18

02 Core Strategy — Recursive Window Splitting

Grailkeeper extracts data by querying time windows and splitting any window that returns a truncated result (i.e. hit the 500k record cap) into two halves, recursively, until every window returns a non-truncated result or max depth is reached.

Splitting Algorithm
def extract_window(start, end, depth):
    result = grail_query(start, end, max_records=500_000)

    if result.truncated and depth < max_depth:
        mid = start + (end - start) / 2
        extract_window(start, mid, depth + 1)  # ← recurse left
        extract_window(mid, end,   depth + 1)  # ← recurse right
    else:
        write_to_output(result.records)        # ← leaf: write records

A 3-day extraction at ~1.5M records/day typically results in 30–35 API calls, 14–16 splits, and completes in 25–30 minutes.

03 API Request Parameters Used

Grailkeeper uses a carefully chosen subset of request parameters, avoiding several that cause issues on some tenants.

POST /query:execute — Grailkeeper Payload
{
  "query":                   "fetch logs, scanLimitGBytes:-1 | filter ...",
  "defaultTimeframeStart":  "2026-04-27T00:00:00Z",
  "defaultTimeframeEnd":    "2026-04-28T00:00:00Z",
  "maxResultRecords":       500000,
  "fetchTimeoutSeconds":    240

  // Intentionally OMITTED:
  // enforceQueryConsumptionLimit — causes HTTP 400 UNKNOWN_COMMAND on some tenants
  // requestTimeoutMilliseconds  — causes constraint violation errors
  // maxResultBytes              — forces full scan
}
scanLimitGBytes:-1 is always injected into the DQL if not already present. Without it, Grail may stop scanning mid-result and return a truncated response even when the record count is below 500k, causing unnecessary splits.
04 Zero-Copy Streaming Architecture

Early versions loaded all records into a Python list in RAM — at 500k records × ~2 KB each, this caused 3–4 GB RAM spikes per window, growing across windows to 16+ GB and triggering OOM kills. The current architecture eliminates all in-memory record accumulation.

Zero-Copy Data Flow
Grail HTTP response  →  /tmp/xxx.json           (disk, streamed in 64KB chunks)
/tmp/xxx.json        →  /tmp/xxx.records.jsonl  (disk, ijson Pass 1: records only)
                        /tmp/xxx.json metadata  (Pass 2: scannedBytes/Records/ms)
/tmp/xxx.records.jsonl  →  exports/{jid}_{name}.jsonl  (disk, direct line-by-line append)

Peak RAM: ~57 MB regardless of response size or window count

Key insight: Pass 3 (reading JSONL back into a Python list) was eliminated entirely. The extractor now receives the JSONL temp file path and streams directly to the output file.

05 HTTP Hang Detection — Watchdog Thread

Grail sends HTTP response headers immediately but can stall for 90+ seconds before sending the response body on large results. TCP keepalive does not detect this as a failure. A dedicated watchdog thread monitors data transfer and forces recovery.

Watchdog Behaviour
1. Watchdog thread starts BEFORE session.get() is called
2. Monitors last_chunk_time every 5 seconds
3. Logs: [watchdog] idle=Xs bytes_so_far=N token=...
4. After 90s with no new data → closes session → raises RuntimeError
5. Window is retried from scratch with a fresh request token
6. Stops cleanly after successful response completion
200 None (empty body) — Grail can return HTTP 200 with no response body. This is an undocumented behaviour that occurs when the Grail scheduler is busy. Grailkeeper detects this and retries the window.
06 Known Grail Behaviours & Workarounds
200 None

Empty Response Body

Grail returns HTTP 200 with Content-Length: None and no body. Occurs on busy scheduler. Not documented.

→ Detect via response.content == b''. Retry window after short delay.

BUSY_SCHEDULER

"Maximum number of concurrent queries reached". Grail has a per-tenant concurrency limit.

→ Retry with exponential backoff. Grailkeeper uses 2s inter-window delay.

Grail stores records in ~1 GB data packets. A window returning 500k records will produce a ~1–1.5 GB JSON response body.

→ Always stream to disk. Never buffer in memory. Use stream=True + iter_content().

Observed TTL is consistently ~318 seconds (5m 18s). The API spec says up to 399s. Poll at least every 60s to stay safe.

→ Grailkeeper polls every 5s while streaming. Token never expires in practice.

07 Verify — Count Consistency Check

After extraction, a Verify query runs | summarize count() against the same DQL and timeframe to compare the extracted record count with Grail's current count.

Verify Query Construction
// Original extraction DQL:
fetch logs, scanLimitGBytes:-1 | filter matchesValue(dt.entity.host, "HOST-xxx")

// Verify DQL (strip summarize/limit/sort/fields, append count):
fetch logs, scanLimitGBytes:-1 | filter matchesValue(dt.entity.host, "HOST-xxx")
| summarize count()

// Note: filter pipes are PRESERVED — only terminal clauses are stripped
Expected delta: A small positive delta (Grail count > extracted count) is normal and expected. During a 25-minute extraction, new records continue to be ingested into Grail. Grail's eventual consistency also means records written just before extraction started may not have been visible to all query windows. A delta < 1% is considered a perfect match.
count() returns a string: The count() aggregation result in records[0]["count()"] is returned as a JSON string (e.g. "742311"), not a number. Always parse with Number() before arithmetic.
